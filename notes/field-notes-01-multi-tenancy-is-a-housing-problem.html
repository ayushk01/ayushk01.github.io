Field Notes #01: Multi-tenancy is a housing problem

Three ways to keep every customer's data apart in one system, explained as houses, flats and a hostel, and four rules for living in the cheapest one.

Field Notes is a series of short, plain-language explainers on how software is built. Each one starts with a picture and ends with a rule you can use.

Any software that serves many customers from one system has to answer a simple question: where does each customer’s data live? Engineers call each customer a tenant, and the answer a tenancy model. There are three common answers, and they map almost exactly onto housing.

A house each: a database per tenant

Every customer gets their own database. Own walls, own lock. It’s the strongest separation you can buy: a problem in one house stays in that house.

The cost is that everything happens N times. A new customer means building a new house. A migration, which is a change to the structure of the database, has to run once per customer. Backups, monitoring and connections all multiply the same way.

Flats in one building: a schema per tenant

One database, but each customer gets their own schema: their own set of tables inside it. Shared foundation, own front door.

It’s cheaper to run than houses, and a customer’s tables are still theirs alone. But repairs still go flat by flat, and a database holding thousands of schemas becomes slow to manage.

One hostel, a tag on every locker: a shared database

Everyone lives in the same tables. Every row carries a tag saying whose it is, usually a customer id.

This is the cheapest by far. A new customer is a few rows, and a repair happens once. That’s why most small teams start here. The catch is that the tags are the only wall. Nothing in the building stops you opening the wrong locker. One missed check, and a customer sees someone else’s data.

Four rules for living in a hostel

  1. Check the tag at the front door. Work out which customer a request belongs to once, where it enters the system, and pass that down. Don’t let every part of the code work it out on its own.
  2. Make the tagged path the easy one. If reading data without the tag takes extra effort, a mistake stands out in code review.
  3. Add a second lock. Where the database can help, let it. PostgreSQL’s row-level security can enforce the tag inside the database itself, so one missed filter isn’t the only wall.
  4. Plan the move-out early. A few guests always outgrow the hostel. Design “give this customer their own house, running the same code” before anyone needs it.

The rule

Pick your model by what a wrong tag would cost you. For patient records or money, build houses, or at least flats. For a to-do app, the hostel is fine. Just check the tags.
