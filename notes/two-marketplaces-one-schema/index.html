Two marketplaces, one schema

Modeling carpooling and peer-to-peer car rental in a single PostgreSQL schema: what to share, where to diverge, and migration discipline.

Letsdrive was two marketplaces in one app. One side is carpooling: a driver posts a trip along a route, riders book seats, money and a chat thread follow. The other is peer-to-peer car rental: an owner lists a vehicle, a renter books it for a span of days, money and a chat thread follow. I built the backend alone over roughly two years — TypeScript, Express, Prisma, PostgreSQL — and the central design question, the one that shaped everything after it, was whether these were one system or two.

The temptation to fork

The first instinct is to build two systems. Carpooling and rental feel different. A trip has an origin, a destination, a departure time, a seat count. A rental has a vehicle, a pickup window, a return window, a daily rate. The booking semantics differ — seats versus exclusive possession of a car. So you sketch two services, two sets of tables, two payment flows, and you tell yourself they’ll stay cleanly separated.

They won’t. Look past the booking object and the two marketplaces are mostly the same product. A user is a user whether they’re offering a ride or renting out their car — same identity, same auth, same Stripe account, same payout history. A vehicle in a carpool trip and a vehicle in a rental listing are the same physical thing with the same documents. Chat is chat. Reviews are reviews. Locations are locations. Fork, and you duplicate all of that — two user tables, two payout reconciliations, two chat stacks, maintained forever, drifting apart.

So: one schema. Thirteen models. The discipline was deciding, per entity, whether it’s genuinely shared or genuinely divergent, and refusing to fudge that line.

Where they share

Most of the schema is shared, and shared cleanly — not “shared with a type flag and conditionals everywhere,” but shared because the entity is actually identical across both sides.

  • User — one identity, one profile, one Stripe account. A user can be a carpool driver on Monday and a car renter on Tuesday with no second account.
  • Vehicle — owned by a user, carrying registration and documents. The same row backs a carpool trip and a rental listing.
  • Payments and payouts — one Stripe integration. Money in from a rider or renter, payout out to a driver or owner. The reconciliation logic doesn’t care which marketplace generated the charge; it cares about a payable party and an amount.
  • Chat — one Socket.io layer, one message store. A conversation is attached to a booking; the booking’s type is irrelevant to delivering a message.
  • Reviews and Locations — a review is from one user about another after a completed transaction; a location is a place.

The payoff is concrete. Stripe payouts work identically on both sides because there’s one payout path. Trust signals — your rating, your trip history — accumulate across both marketplaces instead of being split across two thin profiles.

Where they must diverge

The divergence is real and I didn’t try to collapse it. A carpool trip is a journey: route, departure time, seats available, per-seat price. A rental booking is a duration: start date, end date, daily rate, exclusive hold on a vehicle. Different shapes with different invariants — you can’t oversell exclusive possession of a car the way you book the third of four seats.

The discipline was to let the booking layer diverge while keeping everything underneath shared. Rather than one bloated table with nullable columns for both worlds and a type enum gating half the fields, the trip-shaped data and the rental-shaped data live in their own models, each pointing back at the shared User and Vehicle. A booking references one or the other. The shared entities never learn which marketplace they’re serving.

The rule that kept this honest: a conditional belongs in the booking layer, never in the shared layer. If I caught myself writing if (type === 'carpool') inside user, vehicle, payment, or chat code, that was a signal the divergence had leaked where it didn’t belong, and I pushed it back up.

Migration discipline across 30+ migrations

A thirteen-model schema doesn’t arrive whole. It grew across more than thirty migrations, and the only thing that kept that survivable was treating every migration as forward-only and small. Each one did one comprehensible thing — add a model, add a column with a sane default, add an index — and was reviewed as such.

The hard rule: never edit a migration that has run anywhere. Prisma’s history is a checksum chain; rewriting an applied migration breaks it. When something needed changing, the change was a new migration, even when that felt verbose. Required columns went in two steps — nullable first, backfill, then enforce — so a deploy never failed against existing rows. Boring, and boring is what you want when the same Payout table moves real money on both sides of the marketplace.

Real-time touches the model

Two real-time features reach into the schema. Socket.io chat is the easy one: a message attaches to a booking, so the model already had the join it needed, and the type-agnostic chat design meant the socket layer never branches on marketplace.

Live trip tracking is the carpool-specific one, and it’s where I was deliberate about not writing to Postgres on every event. A driver’s position updates constantly during a trip — ephemeral, high-frequency data that doesn’t belong in a relational table taking a write per second. So the live stream flows over the socket and stays in memory; the durable schema records only the things that have lasting meaning — the trip, its status transitions, its completion. The model holds what’s true after the trip ends, not every coordinate along the way.

What I’d tell myself again

One schema was the right call, and the reason is maintenance, not elegance. Sharing User, Vehicle, payments, and chat meant one Stripe integration, one chat stack, one reputation system — each built and reasoned about once. The cost was discipline: keep divergence in the booking layer, keep the shared core conditional-free, keep migrations small and forward-only. Pay that cost and two marketplaces fit in one coherent model. Skip it and you’ve just built two systems that happen to share a database.
