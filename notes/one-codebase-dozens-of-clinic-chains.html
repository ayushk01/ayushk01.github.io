One codebase, 2,000+ clinics

How a single multi-tenant frontend serves 2,000+ clinics and hundreds of thousands of patients without per-client forks: resolve the tenant once, then thread it through everything.

On this platform, one React/TypeScript frontend serves 2,000+ active clinics, thousands of doctors, and hundreds of thousands of patients across 100+ specialties. There is no tenant-acme branch, no clinic-foo fork, no client-specific build. The same artifact ships to everyone, and what makes one organisation look and behave differently from another is data, not a different copy of the code. I’m one of the principal contributors to this platform and lead the team that builds it, and the discipline behind that sentence is most of the work.

Why forking per client rots

The tempting first move, when a new chain wants a different color, a different intake flow, one field hidden, is to branch. It feels fast. It is fast — once. Then you have two codebases that drift. A security fix has to be cherry-picked across N forks. A bug reproduced in one is silently alive in the others. Onboarding a new chain means copying the closest fork and editing it, so every client inherits the accidents of whichever client it was cloned from.

The cost isn’t linear, it’s multiplicative: every change has to be reasoned about times the number of forks, and no one holds all of them in their head. For an EHR, where two tenants seeing each other’s data is the worst thing that can happen, that drift isn’t a maintenance annoyance — it’s a liability. So forking was never on the table. The constraint was the design: one codebase, all tenants, all the time.

Resolve the tenant once

The single most important decision is where the tenant gets resolved. The answer: once, as early as possible, before the app renders anything that depends on it. You resolve the tenant from the request context into a single object, and everything downstream reads from that object instead of re-deriving identity on its own.

The rule that follows is the one that matters: nothing below this provider invents its own notion of “current clinic.” Theming, feature flags, permissions, and every API call read the tenant from this one resolved context. There is exactly one source of truth, established before the first screen paints.

Thread the context, don’t re-derive it

Once the tenant is a value, the things that vary per chain stop being special cases and become consumers of that value.

Theming is a set of tokens on the context — colors, logo, layout density. Components read tokens, never a client name. A button doesn’t know which chain it’s rendering for; it reads theme.primary.

Feature flags are a capability set, not a pile of if (tenant === 'x') checks. The component asks “is labResults enabled?” and the answer happens to depend on the tenant. The component never names a tenant.

Permissions come from the same context as a matrix. The UI gates on capability — “can this role discharge a patient?” — and the tenant supplies the answer.

Data access is the one that has to be correct, not just convenient. Every request carries the tenant identity, the server enforces isolation, and the client never assembles a query that could reach across tenants because it has no API surface to do so.

Make isolation the path of least resistance

The failure mode in multi-tenant systems is case-by-case discipline: “remember to scope this query by tenant.” Humans forget. The fix is architectural — make the correct thing the only easy thing. The data layer takes the tenant from context automatically, so the default call is already scoped, and an unscoped call requires going out of your way and would stand out in review. You don’t pass the tenant id by hand on each call, which means you can’t forget to. Correct isolation isn’t remembered; it’s the shape of the API you’re handed.

Branding and layout are data, not code paths

Underneath sits a shared design-system layer. Differences between chains live as theme tokens and configuration — logo, palette, which modules appear, field labels, layout choices — fed into the same components. There is one code path; the chains differ in the data flowing through it. When a difference between two clients is expressed as a branch, you’ve created a fork. When it’s expressed as a row of config, you haven’t.

Onboarding a new chain is configuration, not a release

Because branding is tokens, capabilities are flags, and access is enforced server-side from a resolved identity, adding a chain means producing a configuration: its theme, its enabled features, its permission matrix, its tenant identity. No code changes. No build. No release. The same artifact already in production resolves a new tenant and renders it correctly.

That is the payoff. The hard part was never making one clinic’s UI look right — it was refusing, every single time, to let “just for this client” become a code path. Hold that line and thousands of clinics run on one codebase. Relax it once and you’re maintaining forks forever.
