## The product

Docplix is a healthtech company building an EHR platform used by clinics across India. The clinician-facing surface is the web app, plus a family of React Native mobile apps for patients and clinicians (see the [mobile case study](/work/docplix-mobile/)).

I joined as an intern in March 2022 and converted to full-time the following year. Over ~4 years I've become the **#1 all-time contributor to the core platform — ~1,722 commits, about a quarter of a 6,845-commit codebase** — and I now lead the engineering team that ships it. My role spans architecture, backend, frontend, mobile, the AI stack, and cloud.

**Scale.** This is a production EHR, not a demo. Today it runs **~2,160 active clinics and hospitals, ~2,100+ practising doctors, and ~770,000 patients across 100+ medical specialties**, processing **~30,000 appointments a month** (740K+ all-time, 560K+ prescription line-items, 500K+ documents) — on a single shared multi-tenant MySQL (organisationId isolation, 1,000+ tables, per-org modules and branding), plus a **white-label layer of ~45 custom-branded deployments** including internationally rebranded sales (a French-market product). The platform work earned The WoW Machine Award, Docplix's internal recognition for building scalable systems (Jan 2023).

## End-to-end ownership

When I joined, the platform was small. Over the following years I built and grew it across the whole stack — the repo and build tooling, routing and auth, the design system, the backend APIs, the data model, the mobile apps, and the cloud underneath — into something the team ships on a regular cadence.

What I own:

- **Architecture and tooling.** Framework choices, build setup, folder structure, and the conventions the team still uses today.
- **Auth and access control.** Login, session refresh, role gates, audit trails — the bits clinicians don't notice when they work and immediately notice when they don't.
- **Design system.** The component library, design tokens, and theming primitives the entire app is built from.
- **Backend and data layer.** Node.js + Express APIs over a shared multi-tenant MySQL (Sequelize), real-time over Socket.io, background jobs on Redis/Kue, and a typed client between web, mobile, and the API.

## Multi-tenant platform

The biggest piece of engineering work has been building and scaling a real multi-tenant SaaS. One codebase powers the flagship Docplix EHR and ~45 clinic-branded white-label deployments — each with its own branding, configured feature set, and tenant-isolated data, all served from one build pipeline over a single shared MySQL.

The point of getting the multi-tenant model right: the marginal cost of onboarding a new clinic drops from "months of bespoke work" to "fill in a config and flip a flag." That's the difference between an EHR that has to fork code for every customer and one that scales horizontally — the reason the platform sustains ~40–65 new clinics a month.

## A few hard things

**Theming.** Easy to get wrong on the first pass. We started with compile-time CSS tokens — one bundle per tenant — and rewrote it the moment we hit the third tenant and realized the build matrix was untenable. The version that stuck: CSS custom properties resolved at request time from tenant config, no per-tenant builds. Adding the next tenant became a config change instead of a release.

**Auth boundaries.** Getting tenant scoping right is the kind of thing that's invisible when it works and catastrophic when it doesn't. We pushed the tenant context as high in the React tree as possible, made the typed REST client refuse to fire requests without a tenant in scope, and added a linting rule that catches the one shape of mistake that would have leaked data across tenants.

**Feature flags.** A per-tenant feature-flag layer on top of our config service, so a clinic can opt into newer modules without affecting others. Sounds simple. It isn't — the gnarly part is letting non-flagged code paths assume features exist while flagged paths gate them gracefully, without scattering `if (flagged) {}` everywhere.

## Healthcare interop & clinical AI

The parts I'm proudest of are the specialized, hard ones:

- **FHIR R4 / HL7 for India's NDHM/ABDM.** Compliant DocumentBundles, validation, and terminology, so the platform plugs into the national digital-health network — the kind of interoperability work that's a moat in healthtech.
- **An in-house clinical AI & speech stack** (Python): an **AI medical scribe ("Pāṇini")**, **Whisper fine-tuning**, and **speech-to-text** for ambient clinical documentation inside the EHR.
- **React Native apps** — clinician (per-specialty Rx) and patient apps live on the App Store and Play Store; Hermes engine, native modules, Fastlane CI, CodePush OTA.

## Tech-lead initiatives

Beyond features, I've driven the platform-level work: consolidated the GitHub estate into one org, redesigned the ticket/issue architecture, led a fork-consolidation effort and an **AWS cost-optimization that cut spend ~50%**, optimized the PDF engine, and migrated the mobile apps from React Native 0.66.9 → 0.77.2.

## Stack

- **Frontend:** TypeScript, React, Redux, React Native (Hermes, Fastlane, CodePush), i18next.
- **Backend:** Node.js + Express, Socket.io for real-time, Redis/Kue for background jobs, JWT auth.
- **Data:** MySQL + Sequelize (1,000+ tables, organisationId tenant isolation); Redis for caching.
- **AI:** Python — Whisper fine-tuning, speech-to-text, and the "Pāṇini" clinical scribe.
- **Interop:** FHIR R4 / HL7 for NDHM/ABDM.
- **Infra:** AWS — EC2, S3, Polly, Translate, CloudWatch.
