---
title: "What multi-tenant frontends taught me about feature flags"
blurb: "Per-tenant flags sound easy. The gnarly part is letting non-flagged code paths assume features exist."
date: "2026-05-13"
---

The naive way to do per-tenant feature flags in a frontend is to scatter `if (flagged) { … }` throughout the codebase. Every branch becomes a `flagged ? newPath : oldPath`. A year in, no engineer can confidently say what any specific tenant actually sees on any given screen.

The version that worked, for us:

1. **Flags are a layer, not a sprinkling.** The feature-flag service is a single React provider at the root of the tree. Code below it doesn't see flag values — it sees *resolved* feature objects. Either the feature is on (in which case you get its config), or it isn't (in which case its module isn't even mounted).

2. **Default path assumes the feature exists.** Code paths that don't gate behind a flag are always written as if the feature is available. Flag-gated paths handle the absence. This means "the new module" is the default in 100% of the code; the conditional is the *legacy* fallback, not the new feature.

3. **Sunset is part of the flag definition.** Every flag we ship has a target removal date in its config. If it's still alive past that date, it shows up in a weekly engineering review. Most either get fully rolled out (and the gate gets removed) or get fully reverted. The dead-in-the-middle state is what kills you.

The pattern works for tenant-level flags, A/B tests, and dark launches with minor tweaks. The architectural insight is the same: don't let conditionals leak into the modules that benefit from them.
